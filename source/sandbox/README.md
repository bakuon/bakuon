# 关于 QtRO 拓扑结构
是否引入 QRemoteObjectRegistryHost（注册中心宿主）代表了两种截然不同的分布式/跨进程设计哲学：“动态发现的中心化星型拓扑” 与 “静态绑定的点对点直连拓扑”。
为了让架构选型时清晰明了，我们直接看它们的本质区别、运行机制以及在“进程沙箱”场景下的抉择。

------------------------------
## ⚖️ 1. 核心技术对比与本质区别

| 维度         | 不使用 Registry（点对点直连模式）                                                                     | 使用 Registry（中心化动态注册模式）                                                                              |
| ------------ | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 拓扑结构     | P2P 点对点（Point-to-Point）。                                                                        | 星型拓扑（Hub-and-Spoke）。                                                                                      |
| 连接机制     | Replica（客户端）必须在代码里写死并显式连接到 Source（服务端）的特定物理 URL（如 local:my_channel）。 | Source 和 Replica 都只连接到 Registry。Replica 只需要通过类名/对象名向 Registry 订阅，由 Registry 动态撮合连接。 |
| 寻址感知     | Replica 必须预先知道每个 Source 的确切地址。                                                          | 双方对彼此的具体 IPC 通道/网络 IP 端口完全无感。                                                                 |
| 节点生命周期 | 连接是静态的。若 Source 重启，Replica 需要感知连接断开并尝试重连该固定地址。                          | 节点天然支持热插拔。Source 随时可以上线或断开，Registry 会将变更实时广播给所有订阅者。                           |

------------------------------
## 🔄 2. 两种模式的数据流向与运作机制
## 模式 A：不使用 Registry（直连模式）
这正是我们当前沙箱骨架代码中采用的方式。

   1. Host 为子进程生成一个唯一的地址 local:SandboxChannel_123，并通过命令行传给 Sandbox。
   2. Sandbox 启动，在 local:SandboxChannel_123 开启监听（Source）。
   3. Host 直接连接 local:SandboxChannel_123（Replica）。


* 特点：直接建立通信管道，没有中间商，简单高效。

## 模式 B：使用 Registry（注册中心模式）

   1. 主程序启动一个全局唯一的注册中心：QRemoteObjectRegistryHost，监听在 local:MainRegistry。
   2. 随后启动的 Sandbox 子进程（Source）连接到 local:MainRegistry，并向其宣告：“我是 PluginControlSource 类型的节点，我在线”。
   3. Host 进程（Replica）也连接到 local:MainRegistry，并向其申请：“我要一个 PluginControlSource 类型的节点代理”。
   4. 注册中心（Registry）在后台进行地址撮合，让 Host 与 Sandbox 握手建立连接。


* 特点：引入了一个中介服务（类似于服务发现 Nacos 或 Consul 的轻量级单机版）。

## 🎯 3. 应用场景深度对比

## 场景 1：不使用 Registry 适合什么？（强烈推荐用于“进程沙箱”架构）

* 多实例且生命周期强绑定的沙箱：在沙箱架构中，主程序（Host）往往需要同时拉起多个第三方插件进程（例如同时拉起 3 个独立的渲染插件进程）。
* 为什么更优：如果不用 Registry，Host 可以为每个子进程分配一个独立的、私密的本地管道名称（如 local:sandbox_1、local:sandbox_2），实现一对一的精准控制和生命周期隔离。
* 避免命名冲突：如果使用了 Registry，当 3 个沙箱进程同时启动并向同一个注册中心宣告“我是 PluginControlSource”时，Registry 默认会产生命名冲突或模糊路由，导致 Host 很难在不引入复杂 GUID 的情况下精准区分“哪个 Replica 对应哪个 QProcess 子进程”。

## 场景 2：使用 Registry 适合什么？

* 分布式系统或多独立组件协同：你的系统由多个相互独立的团队开发的软件组成。例如：一个“主控程序”、一个“硬件驱动服务进程”、一个“算法分析进程”、一个“日志监控进程”。
* 为什么更优：这些进程的启动顺序不确定，可能先开驱动，也可能先开算法。此时，在系统后台挂一个 QRemoteObjectRegistryHost，任何一个组件启动时只需要往注册中心一挂，其他组件就能“动态发现”并直接调用它，极大降低了系统组件之间的网络寻址耦合度。

------------------------------
## 👑 选型结论
针对正在构建的“多进程沙箱隔离插件框架”，坚定选择不使用 RegistryHost 的直连模式。
**原因在于：** 在沙箱框架中，沙箱子进程（Sandbox）是主程序（Host）的附属品（Slave），它的生命周期完全由 Host 通过 QProcess 强力掌控。Host 知道沙箱什么时候生、什么时候死，因此 Host 天然拥有最高的控制权，直接使用显式命令行传参 + 点对点直连是最稳健、性能损耗最小、最不容易发生多插件命名冲突的黄金设计。

------------------------------
## 选型路线图
在设计通用扩展点框架时建议采用以下黄金组合方案：
1. **控制与生命周期管理层（使用 Qt Remote Objects）：**

   主程序（Host）作为 QRemoteObjectHost，插件沙箱（Sandbox）作为 QRemoteObjectNode。双方通过本地命名管道（local:registry）连接。所有的初始化、控制、状态变更、进度条刷新、日志上报，全部通过 QtRO 的 .rep 契约自动同步。

2. **核心数据传输层（使用 QSharedMemory）：**

   如果扩展点涉及大文本、音视频、点云、图片等大数据传输，在 QtRO 的契约中只传递一个 QString memoryKey。当 Host 触发 executeCommand(memoryKey) 时，插件去挂载对应的 QSharedMemory 块，直接做原地高吞吐计算。
